# Протокол экспериментов и приёмка

Статус: запланировано, не выполнено. Ни одна метрика в этом документе не является измеренным результатом.

## Проверяемые гипотезы

| ID | Гипотеза | Проверка |
|---|---|---|
| H1 | Комментарии позволяют обнаружить ошибки мышления, которые не видны из одного PGN | Сравнить разбор с комментариями и без них на размеченных мыслях |
| H2 | Профиль автора добавляет пользу сверх обычного тренера с движком | Слепое сравнение трёх конфигураций на одинаковых позициях |
| H3 | Профиль обобщает наблюдения на новые эпизоды | Проверка на целиком отложенных видео-группах |
| H4 | Запись событий позволяет надёжно связать речь с позицией | Сравнение с ручной разметкой записи экрана и микрофона |
| H5 | Более дешёвая диалоговая модель сохраняет полезность | Сравнить модели при одинаковых данных, профиле, поиске и бюджете движка |

## Наборы данных

### Пилот

- По 3 видео каждого автора, с достаточным числом объясняемых позиций. На пилоте одно видео каждого автора отложить целиком; двух оставшихся достаточно для проверки процесса, не для заявления о полном характере.
- 3 собственные партии рапида с аудио; по возможности записать экран OBS как независимый эталон времени.
- Вручную разметить минимум 30 учебных эпизодов суммарно и 30 содержательных мыслей игрока. Если пригодных эпизодов меньше, увеличить пилотный набор и зафиксировать причину.

### Приёмочный набор

- 10–20 видео на автора. Не менее 20% групп держать в holdout, при малом корпусе минимум 2 группы на автора.
- Минимум 50 тестовых разборов мыслей из минимум 5 собственных партий. Партии, использованные для настройки prompts, не включать в итоговый blind test.
- Минимум 40 отложенных учебных эпизодов, по 20 на автора, для проверки переноса профиля.
- Минимум 100 реплик для проверки синхронизации, включая границы ходов, паузы и переподключения.

Нарезки одного стрима, повторные показы и дубли партий объединяются в split_group. Holdout не участвует в построении профиля, индексе поиска и выборе примеров prompt. Публичное происхождение видео не исключает возможное знакомство базовой LLM с ним; поэтому абсолютную независимость от предобучения не заявлять.

## Эталон и разметка

Для каждой мысли: исходная реплика, позиция, связь во времени, тип утверждения, ожидаемая оценка, существенная ошибка/верная часть, допустимые объяснения и проверенная линия при необходимости.

Для эпизода автора: показанная позиция, обсуждённые кандидаты, аргументы, акценты, практический выбор и оговорки. Слова автора и разметка аналитика разделены.

Владелец оценивает полезность и соответствие наблюдаемым объяснениям. Шахматные утверждения проверяются движком и ручным просмотром; спорные стратегические выводы помечаются unresolved. Независимый тренер желателен для таких случаев, но его участие не считается уже обеспеченным. LLM-судья помогает сортировать ответы, но не является единственным основанием приёмки.

## Эксперимент с профилем

| Конфигурация | Доступный контекст |
|---|---|
| A | Позиция, мысли игрока, движок, общий тренер |
| B | Всё из A + найденные эпизоды автора |
| C | Всё из B + проверенный обобщённый профиль автора |

Зафиксировать одну модель и движковый бюджет для A/B/C. Перемешать ответы, скрыть названия конфигураций, убрать случайные подсказки вроде имени автора. Оценивать независимо: точность, полезность для мысли игрока, применимость принципа, характер объяснения. Узнаваемая лексика сама по себе не повышает оценку рассуждений.

На holdout-эпизоде показывать модели позицию и контекст до объяснения автора; скрыть само объяснение и последующий выбор. Сравнить акценты и кандидатов с наблюдаемым продолжением. Несовпадение точного хода не равно провалу, если автор рассматривал несколько разумных кандидатов.

## Кандидаты моделей

| Задача | Сравнение |
|---|---|
| ASR | Deepgram Nova-3 против faster-whisper на одинаковом русском аудио |
| Извлечение эпизодов | Gemini video pipeline против расшифровки + кадров + сильной reasoning-модели |
| Принципы автора | Claude Opus против Gemini на одинаковых verified-эпизодах |
| Диалог | Claude Sonnet, Claude Opus и Gemini при фиксированном профиле |
| Поиск | Полнотекстовый baseline против гибридного BGE-M3 + структурные признаки |

Перед запуском зарегистрировать точные model ID, доступность у аккаунта, параметры, prompt revision и цены. Алиасы «latest» не использовать как единственный идентификатор результата. Повторить 10 наиболее сложных кейсов по 3 раза для оценки нестабильности.

## Метрики и пороги

Пороги — предложенные критерии v1. При их изменении обновляются версия протокола и причина, а не пересчитывается успех задним числом.

| Область | Критерий |
|---|---|
| Легальность | 100% опубликованных вариантов воспроизводятся из указанного корня |
| Привязка | Не менее 95% реплик правильно привязаны или явно помечены неоднозначными; отдельно не менее 80% размечаемых реплик имеют правильную автоматическую привязку без ручной правки |
| Ошибочная уверенность | Не более 5% автоматически уверенных привязок ошибочны на эталоне; ambiguous не считается правильной привязкой в этой метрике |
| ASR | Отдельно измерены WER, ошибки полей/фигур и потеря отрицаний; в тексте после проверки не остаётся известных смысловых искажений |
| Эпизоды | Нет известных ошибок доски/авторства в опубликованном наборе; все v1-эпизоды просмотрены человеком |
| Тактика | Нет критических тактических ошибок в окончательных ответах на 50 приёмочных кейсах |
| Полезность | Средняя оценка владельца ≥4/5 на 50 кейсах |
| Польза профиля | C предпочтительнее A минимум в 60% ненулевых сравнений при минимум 30 сравнениях без ничьей; фактическая точность C не хуже A |
| Обобщение | На 40 holdout-эпизодах C лучше A по совпадению основных аргументов; отдельно публикуются результаты по каждому автору и размер эффекта |
| Устойчивость | Потеря сети и повторные загрузки не уничтожают подтверждённые блоки и не создают дублей |

Критическая тактическая ошибка — нелегальная линия, неправильная сторона хода, ложное утверждение о форсированном выигрыше/мате, пропуск опровержения, меняющий главный вывод, либо приписывание игроку противоположного утверждения из-за неверного отрицания.

Небольшой набор не доказывает отсутствие ошибок в эксплуатации. Отчёт показывает числители, знаменатели, исключённые кейсы и причины; средний балл без распределения недостаточен.

Для H1 отдельно проверить, что модель не считает молчание доказательством ошибки и отличает верный ход по ложной причине от верного рассуждения. Кандидат не проходит приёмку при систематическом нарушении этих условий даже с высоким средним баллом.

## Выбор диалоговой модели

1. Исключить конфигурации, не прошедшие приёмку корректности и полезности.
2. Среди оставшихся выбрать минимальную измеренную цену ответа при отставании полезности от лучшей не более 0,3 балла из 5.
3. При близкой цене выбрать меньшую p95 задержку.
4. Если дешёвые модели не проходят — оставить сильную и показать измеренную стоимость. Бюджет не сокращать скрытым ухудшением качества.

Для ASR выбирать по смысловым шахматным ошибкам и привязке, а не только WER. Для подготовки профилей сначала качество, затем стоимость среди прошедших вариантов.

## Расходы и производительность

Единицы учёта: час исходного видео, verified-эпизод, партия, ответ. Отдельно фиксируются input/output/cache tokens, минуты аудио, количество кадров, повторные запросы, CPU-время и ручные минуты проверки.

Цена = сумма фактически учтённых единиц по сохранённой тарифной версии + оценка неопределённых расходов. Не смешивать подписку на чат с оплатой API. Стоимость сервера и ручной работы показывать отдельно.

Начальные цели для пилота: первый базовый разбор партии до 10 минут, проверенный диалоговый ответ p95 до 30 секунд после готовности engine/context cache. Это цели измерения, не SLA; при непопадании оптимизировать кэш/очереди, затем согласовать компромисс на измерениях.

Месячный лимит пользователем не задан. В настройках обработки необходимы лимиты на пакет и предупреждения о расходах; массовую автоматическую обработку не включать без установленного лимита. Пилотный отчёт должен дать оценку стоимости расширения корпуса до 10–20 видео на автора.

## Форма отчёта эксперимента

Отчёт содержит dataset/protocol/config versions; число входов и исключений; модели и стоимость; распределения качества/задержки; примеры ошибок; A/B/C-сравнение; решение pass/fail/inconclusive и следующую гипотезу.

Если профиль не добавляет пользы, статус H2 — fail/inconclusive. Следующий шаг — проверить эпизоды, условия принципов и retrieval. Не объявлять успех за счёт узнаваемых фраз или автоматически расширять архив.
